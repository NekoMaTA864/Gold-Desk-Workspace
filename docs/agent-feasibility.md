# Gold Desk 三種 Agent：可行性與資料契約草案

2026-10-12 討論稿。這裡的 Agent 是產品功能，不必先拆成三個自主 AI 程式。建議先用可重現的查詢與規則運算完成核心，再讓 LLM 將**已算好的事實**整理成文字。E 的桌面原型已於 2026-10-26 從現行追蹤樹移出，可從 [清理前提交](https://github.com/NekoMaTA864/Gold-Desk-Workspace/tree/7c1c71931b38d7b443d42f3071c273e3bd429678/prototype) 取回；其中數值均為合成展示資料。

## 先做的共同基礎

交易草稿需要 `draft_id`、商品、買賣方向、預計手數、建立時間與版本。分析時再加入有來源與時間戳的報價、指標快照、使用者規則版本、案例資料版本。每次修改草稿或換報價都重新產生分析版本；確認畫面只讀取同一版本的結果，避免新舊資料混用。

責任分界：A 提供整合 API 與解釋服務；B 計算風險及個人規則；C 提供券商報價與委託狀態；D 提供案例搜尋及資料充分性；E 顯示來源、狀態、限制、詳情與五區確認。這份草案不改變現有分工，可在 10/15 JSON 討論時定稿。

## 1. 歷史 Agent

**可行性：高，取決於案例資料品質。** 首版不必使用向量資料庫。用結構化欄位篩選同商品、同方向、相近時間框架與可比較的市場狀態，再對候選案例排序。每筆顯示「相似在哪裡」「有哪些差異」「後續發生什麼」及資料來源；保留正反兩種結果，避免只挑有利案例。

建議首版特徵：方向、預計手數或風險區間、價格相對 MA20 的位置、近期波動分位、最近 3 根 K 棒型態。先選 2–3 個真正有資料的特徵，缺值時降低可比較性，不能當成相同。結果窗口（例如後續 1 小時或 4 小時）與交易成本須由 D 統一，否則案例間無法比較。

需紀錄每筆案例的 `case_id`、來源／版本、特徵快照、距離分數、相似原因、主要差異、觀察窗口、後續結果、缺值欄位。距離分數只用於排序，不是本次交易的成功率。

## 2. 個人化 Agent

**可行性：高，適合先做。** 用受控的選項建立可解釋規則，不開放自由輸入會改變下單行為的語句。首版可選三項：

| 範例條件 | 使用者可調整 | 觸發後動作 |
| --- | --- | --- |
| 預計手數超過個人上限 | 上限手數 | 顯示提醒，要求核對部位 |
| 價格高於或低於 MA20 | 上方／下方 | 顯示提醒及指標時間戳 |
| 最近 3 根 K 棒中至少 2 根陽線或陰線 | 陽／陰 | 顯示提醒及判定的 K 棒區間 |

每條規則有 `rule_id`、版本、啟用狀態、參數、資料來源、觸發狀態與缺值原因。缺資料時標為「無法評估」，不能顯示「未觸發」。手數是使用者自己設定的限額；指標只是條件範例，不是入場建議。首版只做提醒，不自動送單或阻擋（正式阻擋條件由 B 與團隊另定）。

## 3. 回復 Agent（資料不足時的退路）

**可行性：高，但不宜輸出單一交易信心百分比。** 它應回答兩個問題：「現有案例夠不夠拿來比較？」與「不足時還有哪些可核對資訊？」。用 `可參考 / 有限參考 / 資料不足` 三態，加上逐項理由，如案例筆數少、特徵缺值、波動差距大、資料太舊或報價過期。資料不足時顯示 B 的風險計算、個人規則與市場快照；若相應資料也缺失，直接標示未知。

首版門檻應由 D 依資料覆蓋率與實際回測定義，不在前端硬編。例如「至少 N 筆可比較案例」只是待討論參數，不應自行宣稱 N 筆就足以預測。本功能的「信心」應是**對資料可參考程度的信心**，不是交易獲利機率。LLM 失敗時仍可輸出固定模板和原始欄位。

## 建議的整合回應

以下是欄位形狀，不是已凍結 API。數值金額與手數用十進位字串，時間用帶時區的 ISO 8601，避免 JS 浮點數及時間歧義。

```json
{
  "draft_id": "DEMO-ORDER-018",
  "draft_version": 2,
  "analysis_version": "v0.1",
  "quote": {
    "source": "broker_simulation",
    "observed_at": "2026-10-12T10:42:18+08:00",
    "status": "fresh",
    "price": "2651.80"
  },
  "risk": { "status": "available", "summary": "由 B 的計算服務提供" },
  "rules": [
    { "rule_id": "max_lots", "version": 1, "state": "triggered", "reason": "0.40 > 0.30 lots" }
  ],
  "history": {
    "searched_count": 18,
    "comparable_count": 7,
    "cases": [
      { "case_id": "H-204", "similarities": ["同方向", "同均線位置"], "differences": ["波動較低"], "outcome_window": "1h", "outcome": "展示資料" }
    ]
  },
  "sufficiency": { "status": "usable", "reasons": ["特徵覆蓋率達門檻"], "method_version": "pending-D" },
  "explanation": { "status": "available", "text": "展示文字", "source_refs": ["H-204", "max_lots"] },
  "order": { "connection": "not_connected", "submission": "not_submitted" }
}
```

需統一的錯誤／空值：`loading`、`available`、`unavailable`、`stale`；案例零筆是正常空集合，不是 API 錯誤；LLM 失敗不抹除 B／D 已算好的結果；券商委託狀態未知與確定拒單需分開。案例與規則 ID 在文字中應能開啟原始詳情。

## 推進順序

1. **本週可展示**：桌面原型及上述 JSON 範例，讓組員直接看五區摘要和例外情境。
2. **10/15 前討論**：請 B／C／D 各回一份真實欄位的範例 JSON，A 確認整合版本與錯誤狀態；E 將原型欄位對齊。
3. **下一個可整合切片**：先做個人手數上限提醒與歷史案例明細，再接資料充分性判斷；保留無案例及 LLM 失敗退路。

## 成功條件

使用者能辨識展示／即時圖表／券商報價的差異；看得到每條提醒的參數與判定原因；每個案例能回查來源和差異；無案例時不顯示虛構結果；報價過期或券商斷線時清楚指出需要重新檢查的原因。
