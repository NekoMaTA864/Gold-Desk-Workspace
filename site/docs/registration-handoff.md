# 帳號註冊介面與 A 後端銜接

目前只有**前端本地展示帳號**。使用者可以註冊，並以帳號名稱或電子郵件加密碼登入展示工作台。資料只放在這次頁面開啟期間的 JavaScript 記憶體，重新整理就會消失；沒有呼叫 API、建立後端帳號或提供真正的驗證與權限保護。展示密碼也暫存在記憶體，請勿輸入平常使用的密碼。合成交易資料目前不依展示帳號隔離。

舊版五人分工表寫的是「A 只做團隊預設帳號，不做註冊」。新增註冊由新討論提出，接線前請團隊先決定是否開放自行註冊，或僅接受邀請碼／管理者建立帳號。介面可保留同一組欄位，依決定加上邀請欄位或關閉提交。

## 畫面流程

1. 展示入口提供「登入／註冊」切換，合成展示仍不需帳號。
2. 註冊輸入帳號名稱、電子郵件、選填顯示名稱、密碼與確認密碼。帳號名稱 3–24 個字元，不含空白或 `@`；展示密碼至少 8 個字元，不要求字元種類。預設角色顯示為一般使用者；操作者身分不能由表單選取。
3. 登入使用同一個「帳號或電子郵件」欄位加密碼。展示登入後的標籤只表示本地流程，不代表後端身分，交易資料仍共用。
4. 接線後提交時顯示處理中，避免重複送出。成功後依 A 的回應顯示「請驗證信箱」或「可登入」；失敗時顯示可恢復的錯誤。正式密碼規則由 A 決定並由後端執行，不可只依賴前端的 8 字元檢查。
5. 正式登入狀態與權限應以後端回傳為準。前端不得用本機欄位值或 `localStorage` 自行判定為操作者。

## 建議與 A 約定的資料契約

下列只是討論起點，路徑與欄位名稱由 A 的實作決定。

```json
POST /auth/register
{ "username": "...", "email": "...", "display_name": "...", "password": "..." }

POST /auth/login
{ "identifier": "帳號名稱或電子郵件", "password": "..." }
```

回應至少要讓前端分辨「已接受註冊，待驗證」、「可登入」及「暫時無法完成」。帳號與電子郵件應由後端各自檢查唯一性，並約定大小寫和正規化方式。正式錯誤回應應避免透露帳號或郵件是否存在。角色由後端設定；註冊請求不帶 `role`。前端只做使用體驗檢查，後端仍要獨立驗證輸入、限制頻率、保護密碼與驗證身分。

## 接線前的決策

- 是否允許公開自行註冊，或需邀請碼／管理者核准？
- 是否要求電子郵件驗證？若要求，驗證完成前能否進入工作台？
- 登入後如何傳回一般使用者與展示操作者角色，以及帳號停用狀態？
- 是否使用同網域的安全 Cookie 工作階段？登出、過期與重新登入的畫面狀態為何？

即使註冊開放，一般使用者仍不可直接送出券商模擬單；送單權限須由 A 的後端再次檢查。
